# 关键代码片段解读（T4-4）

> 选段原则：三段代码分别对应“解包 → 判定 → 策略”主链路；每段讲清楚“为什么这么写”，而不是只贴实现。
> 行号以当前 `master` 为准；代码改动后需同步刷新。

## 片段 1：`src/unpack.py` —— 把不可靠的 binwalk 变成可判定的结构化结果

对应任务：T1-1。关键函数：`unpack_firmware`（[`src/unpack.py:133`](../src/unpack.py#L133)）、`parse_signatures`（[:68](../src/unpack.py#L68)）、`collect_filesystems`（[:87](../src/unpack.py#L87)）。

**为什么这么写**

1. **binwalk 不是稳定 API**。它可能不存在、可能超时、可能对损坏固件返回非 0、也可能成功但没产出文件系统。调用方（后续取证/判定）不应该被迫处理这些差异。`unpack_firmware` 把结果收敛成 `not_found → binwalk_missing → timeout → invalid_image → extract_failed → ok` 六种状态，任何输入都不向调用方抛异常；这是 T1-1 的验收条件，也是 T2/T3 能稳定跑批的前提。
2. **把“工具故障”和“固件损坏”分开**。binwalk 退出码非 0（参数/权限/extractor 加载失败）归为 `extract_failed`，只有“签名都没识别出来”才归 `invalid_image`。这条区分来自真机踩坑：root 运行 binwalk 需要 `--run-as`，失败曾被误报成固件损坏。
3. **文件系统定位不依赖固定层级**。binwalk v2/v3 的目录结构不同，`collect_filesystems` 递归找 `squashfs-root`/`jffs2-root`/`cramfs-root`/`rootfs` 及其带后缀变体，避免把版本差异写死进代码。
4. **结构化产物**。返回 `UnpackResult`（文件系统路径、文件数、组件、错误类型），T1-1 的真实实测数据（AC15 841 文件/1.488 s、DCS-960L 1133 文件/1.432 s）就是由它产出的，而不是人工抄终端。

**解读要点**：这段代码展示的是“把外部工具的失败模式变成数据契约”的做法。没有新增第三方封装，只用了 `subprocess` + `pathlib` + 明确的错误分类。

## 片段 2：`src/exposure.py` —— 阳性发现按风险累计，而不是把 E1 算成 0

对应任务：T2-1。关键函数：`assess_exposure`（[`src/exposure.py:256`](../src/exposure.py#L256)），口径全文见 [`materials/判定口径-T2-1.md`](判定口径-T2-1.md)。

**为什么这么写**

1. **旧公式的语义硬伤**。`docs/00` 原公式 `U = [Σ未覆盖 w + Σ(E2/E3) w·(1−c)] / Σw` 把 E1 排除在两项之外，等于 E1 贡献 0；但 `configs/judgement.yaml` 的 E1 定义是“在影子设备中实际复现该风险”。如果照字面实现，越确定的高危问题越容易放行，三态会反向。因此我把风险项改为：
   - `clear`：0；
   - `not_tested`：`w`（未知按最坏情况）；
   - `found + E1`：`w`（实测确认）；
   - `found + E2/E3`：`w * confidence`（单点/静态，按置信度折算）。
2. **Evidence 只记录阳性发现**。T1-2 的 `Evidence` 没有“测了没问题”的状态；如果直接按“有证据=覆盖、没证据=未覆盖”，就无法区分“没测”和“测了干净”。所以 T2-1 引入显式 `outcomes`（`found/clear/not_tested`），缺省时只把有证据的项记 `found`，其余记 `not_tested`，绝不把“没扫到”自动当 `clear`。
3. **保障度与硬红线**。除了 `U`，还计算加权保障度 `A`：`clear`=1、`found E1`=1、`found E2/E3`=c、`not_tested`=0。判定顺序是：Critical E1 硬拒绝；Critical E2/E3 或 High E1 至少条件；`A < 0.6` 记证据不足；再看 `U` 的阈值。这样“没测”不会被低敞口放行，单条 Critical 也不会被 9 项权重稀释掉。
4. **边界可测**。全 `clear` → pass；全 `not_tested` → conditional（0 置信度）；全 E3 → conditional；全 E1 → reject。`tests/test_exposure.py` 的 11 个用例把这些边界和“unknown check/状态矛盾”都固定住。

**解读要点**：这段代码把“证据等级”从展示字段变成了计算字段，同时保留了 `Evidence` 数据契约不变；`confidence` 是静态初判，不是实测命中率，材料里必须这样写。

## 片段 3：`src/policy.py` —— 端点 → 粒度 → ACL/MUD，回退必须显式

对应任务：T2-2。关键函数：`choose_granularity`（[`src/policy.py:109`](../src/policy.py#L109)）、`build_policy`（[:178](../src/policy.py#L178)）、`endpoints_from_evidence`（[:213](../src/policy.py#L213)）。

**为什么这么写**

1. **粒度选择是判定的一部分，不是格式转换**。默认 FQDN；如果同一厂商的多个域名可归组，选 vendor-group；如果端点是 IP 或域名不可定位，回退 ASN。`choose_granularity` 把这条顺序写成可测试的规则，而不是让调用方每次用 if/else 拼。
2. **`asn-fallback` 必须显式**。`configs/baseline.yaml` 的 `policy.asn_fallback_must_label: true` 是硬约束。`build_policy` 只要最终粒度是 ASN，`Policy.asn_fallback=True`，ACL 规则同时带 `# asn-fallback: no ASN mapping`；不允许“悄悄回退”。
3. **回滚引用必填**。策略不是一张白名单截图，必须能回滚；`rollback_ref` 为空直接 `ValueError`。`Policy` 数据契约里的 `rollback_ref` 在 T2-3 报告里也会展示。
4. **ACL/MUD 同源**。同一批端点既可输出 ACL 行，也可输出 MUD JSON 行；`rule_format` 只改变载体，不改变粒度与端点，避免“报告说 FQDN、策略却按 IP 下发”的不一致。`asn-fallback` 路径由单测覆盖；真实 A1/A2/A3 端点都是域名，所以样例均为 FQDN、`asn_fallback=false`。

**解读要点**：这段代码把 `configs/baseline.yaml` 的策略口径落成可执行函数；`Policy.rules` 仍是 `list[str]`，不引入新的数据模型，T2-3 报告可直接消费。
