## 一、背景与价值

园区、校园与中小企业网络的设备构成正在变化：除了笔记本电脑与服务器，越来越多的摄像头、路由器、打印与门禁终端直接接入办公网。这些设备的采购验收普遍只看功能与价格，安全判断依赖厂商白皮书或事后等保测评，真正决定"这台设备能不能进网、进网后能访问什么"的环节是空的。现存的准入与微隔离方案（802.1X、NAC、微分段）有一个共同前提——**设备必须先在网络上跑起来，才能学到它的通信行为，再据此生成策略**。对于刚到手、尚未部署、或者根本不敢先接网的设备，这类方案拿不到任何证据，只能二选一：要么全放行，要么全拒绝。

本作品把判断点前移到"设备上线之前"。我们下载设备公开固件，在隔离仿真环境里把它跑成一台"影子设备"（FirmAE + QEMU 全系统仿真），对影子设备真实发起请求-响应，拿到可追溯到原文的证据；再把证据按等级折算成风险敞口，输出三态判定（通过 / 有条件放行 / 拒绝）与置信度，并为"有条件放行"的设备的合成一份可下发、可回放、可回滚的最小权限策略。设备还没上电，网管已经拿到判定与策略草稿。

价值体现在三方面。第一是**场景价值**：校园网与园区网每年都有大批新终端与 IoT 设备入网，验收环节缺少可执行的安全判断，本作品把这一步变成"上传固件 → 出结论"的可重复动作。第二是**合规价值**：等保与最小授权要求能给出"为什么只放行这几个目的地址"的依据，本作品输出的是带 raw_ref 的证据链，而不是一句"建议加固"。第三是**可复制性**：数据只依赖厂商官网公开固件与公开漏洞公告，不需要厂商配合、不需要改动被检设备，换一个厂商只需补一条锚点。技术架构上服务端只用 RDS MySQL、Redis 与 ECS 容器，仿真 Worker 留在本地隔离主机，成本与运维门槛都可控。

## 二、创新性

创新点一：**证据分级决策，而不是"扫出一堆 CVE 分数"**。本作品把每条取证结果显式归入 E1（影子设备实测、有报文与响应原文）、E2（仿真成功但只做了单点探测）、E3（仅静态推断，未运行验证）三级，并为"仿真启动失败"定义了强制降级规则：运行期取证一律记 E3 并标 `TODO(measure)`，禁止按 E2/E1 记录。这条规则是整个作品最核心的诚实机制——它从制度上堵住了"静态推断冒充实测结论"这个嵌入式安全领域最常见的注水点。判定置信度由证据等级折算，读者可以逐条追问"这条结论的证据是哪一级、原文在哪"。

创新点二：**在设备上线之前给出准入结论与策略**。微隔离与 NAC 类方案的顺序是"先上线、再学习、后收紧"，本作品把顺序倒过来：设备尚未接入，就用影子设备产生运行期证据，并直接合成策略。这是与行业现有方案的结构性差异，不是性能差异。

创新点三：**策略与判定同源、自带回滚引用**。判定为有条件放行时，策略从影子设备实际观测到的端点出发，按"域名可定位 → FQDN 粒度；域名不可定位 → 回退 ASN 并在报告中显式标注 `asn-fallback`"的顺序选择粒度，载体格式取 ACL 或 MUD（RFC 8520），每条策略必须带 `rollback_ref`，下发后可回放验证拦截效果、可一键回滚。策略不是一张白名单截图，而是与判定共用同一套数据契约的可执行产物。

差异化表述：静态的固件成分分析（SBOM/CVE 扫描）回答"这个固件里有什么漏洞"，本作品回答"这台设备能不能进网、进来只能访问什么"。前者交一张漏洞列表，后者交一份带置信度与回滚路径的准入决定。

## 三、数据集的选取与处理

**数据对象**：设备固件。计划规模为 12 个固件（摄像头 6 / 路由器 6），逐条记录厂商、型号、硬件版本、固件版本、下载链接与许可说明。当前三锚点均已核验：A1（Tenda O4 V3.0，V1.0.0.19(6074)）、A2（D-Link DCS-960L，1.07.102）、A3（Tenda AC15，V15.03.05.18）；**12/12 文件已获取**（6 摄像头 / 6 路由，含 A3 同族对照），文件总大小 116,681,762 字节，完整 SHA-256 与直链见 `materials/固件获取记录.md`、`materials/数据集说明.md`。其中 3 个锚点已核验 CVE 版本；其余 9 个是数据集样本：R1/R2/R3/C1–C5 已解包并生成 E3 证据；C1–C4 因原 D-Link 相机固件无 rootfs 已替换为 Tapo C100/C110/C210/C310；全部新样本尚未跑 FirmAE，许可说明待补。锚点已 ≥3，“锚点判定正确率”有效，尚待判定结果。

**公开参照数据源（只登记外链，不随仓库分发）**：`configs/baseline.yaml` 登记了 8 条，用途各有分工——

- DefaultCreds-cheat-sheet：默认口令对照表，上游自述规模 3,711 条 / 1,398 个产品厂商 / 1,680 个唯一密码（公开文献数字，非本作品实测）；上游声明仅供教育用途，故只外链引用、禁止内置分发；
- RouterSploit：嵌入式设备利用框架，其 exploits / creds / scanners 三分类作为检查项分类依据；
- abuse.ch：出向外联的公开威胁情报对照；
- CVSS v3.1 规范：严重度→权重映射依据（Critical 1.0 / High 0.8 / Medium 0.6 / Low 0.3）；
- NVD、FirmAE、OpenWrt 固件下载：CVE 核对、仿真样本与可复现固件来源。

**处理流程**：① 从厂商官网下载固件并计算 SHA-256（`firmware.sha256`，实测值缺失时写 `TODO(measure)`）；② binwalk 解包定位文件系统，登记解包任务状态（`unpack_job` 表，queued/running/done/failed）；③ 提取指纹与配置（硬编码口令、默认账号、外联地址）；④ 在隔离仿真环境中用 FirmAE/QEMU 启动影子设备，按 9 项检查项（CRED / UNAUTH / EGRESS 三类各 3 项）执行取证，留存报文与响应原文并写入 `evidence.raw_ref`；⑤ 证据分级、计算敞口、出三态判定；⑥ 由判定合成策略。所有中间产物只有一个数据契约（`src/schema.py` 的四个 dataclass），DDL 见 `materials/rds_schema.sql`。

**标注流程**：12 固件 × 9 检查项采用 **“AI 机器预标 + 人工核验”** 的单标注流程；2026-11-22 修正 `src/evidence.py` 后重跑 evidence，A 侧预标为 **39 found / 69 not_tested / 0 clear**，人工核验只对明确证据条目负责。B 侧 AI 辅助判读仅用于工程一致性检查（A/B 规则一致 108/108），**不报告 human-human agreement / Cohen's κ**，也不把它写成“双人标注质量”。coverage 为 **0.3611（39/108）**；真正的人工双标如需，另行组织，不拿机器一致性冒充。数据：`annotator_A.json`、`annotator_B.json`、`metrics_12.json`。

## 四、关键代码片段解读

> 本节只解读仓库中**已存在**的代码（`src/schema.py`、`src/config.py`、`src/unpack.py`、`src/evidence.py`、`src/exposure.py`、`src/policy.py`、`src/report.py`）。三段必选片段（解包 / 敞口 / 策略）的完整解读已落盘到 `materials/代码片段解读.md`；定稿时从该文件摘录，不贴未完成代码。

**片段 1：`src/schema.py` —— 数据契约与取证诚实性**

`schema.py` 用四个 dataclass（`Firmware` / `Evidence` / `Decision` / `Policy`）和四个 `str` 枚举（`EvidenceLevel` / `Verdict` / `Granularity` / `RuleFormat`）定义全系统唯一的数据契约。关键在 `Evidence.__post_init__` 与 `Decision.__post_init__`：

- `_to_enum` 把传入值收敛到枚举成员，非法值直接 `ValueError`，错误信息列出全部合法取值；
- `_check_ratio` 显式排除 `bool`，再要求落在 `[0.0, 1.0]`，把"置信度 >1"这类只有在下游报表里才会暴露的脏数据挡在构造阶段；
- `Decision.exposure` 为可选，但一旦给了值就必须过同一道校验，"未计算"与"算错"因此有明确区分。

解读要点：这套校验把"证据等级"和"置信度"变成了不可绕过的字段约束，而不是靠文档约定。数据库侧 `materials/rds_schema.sql` 对 `level`/`verdict`/`granularity`/`rule_format` 用同值 ENUM、对 `confidence`/`exposure` 用 `DECIMAL(4,3) + CHECK 0..1`，与 dataclass 一一对应——契约在进程内和落库处各锁一次。

**片段 2：`src/config.py` —— 配置即口径，拒绝魔法数**

`config.py` 负责三份配置的加载与结构校验。`load_yaml` 把 YAML 解析失败与非 mapping 根节点统一转成 `ValueError`；`validate_baseline` 做三件关键事：检查项字段完整性（`code/category/name/severity/weight/source`）、检查项 `weight` 必须与其 `severity` 在 `weight_mapping` 中的映射值严格相等、阈值必须满足 `0 < pass_max < conditional_max <= 1`；`validate_judgement` 则强制 `evidence_levels` 恰为 E1/E2/E3 且 `meta.real_device_required` 为 `false`。

解读要点：判定口径与权重不是散落在代码里的常量，而是 `configs/baseline.yaml` 中的数据，代码只校验不重定义。这样"阈值是 provisional、要由锚点集校准"这件事在仓库里可见、可改、可追溯；同时 `real_device_required=false` 的校验让"不碰真机、全部结论来自隔离仿真环境"这条口径无法被悄悄改成真机叙事。`validate_anchors` 还要求已验证锚点必须带 http(s) 下载链接与具体版本，杜绝"TBD 也算已验证"。

**三段解读已落盘**：`unpack.py`（binwalk 封装 + 文件系统定位）、`exposure.py`（风险累计 + 保障度 + 三态）、`policy.py`（端点 → 粒度选择 → ACL/MUD 合成）的“为什么这么写”与行号引用见 `materials/代码片段解读.md`；本节不再贴未完成代码。
