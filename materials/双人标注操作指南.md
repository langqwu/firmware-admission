# 双人标注操作指南（小白版）

> 目标：两个人**独立**给 12 个固件 × 9 个检查项打 `found / clear / not_tested`，再算一致率、Cohen's kappa、覆盖率。
> **2026-11-22 方案一：初赛材料不报告 human-human κ；当前采用 AI 机器预标 + 人工核验。本指南保留为流程参考，真人双标如需要再另行组织。**
> **本轮任务分配：王同学 = A（核验机器预填）；苏同学 = B（独立从空白开始）。** 任务书见 `materials/标注任务分配-王同学-苏同学.md`。
> 适用：Windows + PowerShell，项目目录 `E:\dsh_talking\firmware-admission`。
> 先读一遍再动手；全程约 60–90 分钟/人。不要一边讨论一边标。

---

## 0. 先搞懂三件事

### 0.1 你在标什么

每个固件有 9 个检查项：

```text
CRED_DEFAULT_ADMIN_WEB
CRED_DEFAULT_SERVICE_LOGIN
CRED_HARDCODED_SECRET
UNAUTH_MGMT_ENDPOINT
UNAUTH_COMMAND_EXEC
UNAUTH_INFO_DISCLOSURE
EGRESS_FIXED_CLOUD_ENDPOINT
EGRESS_PLAINTEXT_CHANNEL
EGRESS_UNREGISTERED_THIRD_PARTY
```

每个格子只能填三种值之一：

| 值 | 含义 | 什么时候能填 |
|---|---|---|
| `found` | 找到了这个风险 | `materials/` 里有对应证据条目，能看到 `level/confidence/raw_ref` |
| `clear` | 实际测过，确认没有 | 你**真的执行了**对应检查并留下记录（命令/日志/响应） |
| `not_tested` | 没测/没有证据 | 默认值；不确定就填这个，不要猜 |

### 0.2 不要做的事

- 不要把所有格子都填 `clear`。
- 不要把 E3 静态发现说成 E1 实测。
- 不要因为“没搜到”就填 `clear`；没测就是 `not_tested`。
- 不要看对方的标注，也不要先看 `materials/decisions/`（会污染独立判断）。
- 不要在 JSON 里留 `TODO`；脚本会直接报错。

### 0.3 现在项目里大部分格子会是 `not_tested`

这是正常的：目前只有 A2 有真实运行时 E1/E2（DCS-960L 默认口令 + HNAP），
其他固件主要是静态 E3。`clear` 需要真实测试记录，不要为了“好看”硬填。
覆盖率低是事实，不是你的错；材料里要如实写。

> **A 的文件已经由 evidence 自动预填**（`annotator_A.json` / `machine_prelabel_A.json`）：
> 有对应 `check_code` 证据的格子是 `found`，其余是 `not_tested`，没有 `clear`。
> A 的工作是**逐条核对 raw_ref、纠正错误**，而不是从零猜。
> 这份预填是“机器初标 + 人工核验”的辅助，**不是 A 独立人工首标**；材料里要如实写。
> B 的文件仍是全 `TODO`，必须独立人工标注，不能看 A 的预填结果。
>
> 为什么不让我把 A/B 都填了：双人标注的意义是“两个独立判断”，AI 只能做预填/审计，
> 不能冒充第二个独立标注员；否则 kappa 是假的，评审一问就穿。

## 1. 角色与纪律

| 角色 | 做什么 |
|---|---|
| 标注员 A | 核验 `annotator_A.json` 的机器预填，逐条看 raw_ref 后人工确认 |
| 标注员 B | **从 TODO 开始**独立填 `annotator_B.json` |
| 仲裁人 C | 只看 A/B 不一致的格子，依据 evidence 决定最终值 |

纪律：

1. A、B 各自完成后才交换文件；
2. 中途不讨论具体固件/检查项；
3. 仲裁人只处理不一致项，不重标全部；
4. A/B 原始文件**永远不要覆盖**，否则 kappa 会失真。

## 5. 手把手：把 12 台都标完

### 5.1 推荐顺序

先锚点，再其余：

```text
A1 → A2 → A3 → A3-19
→ R1 → R2 → R3
→ C1 → C2 → C3 → C4 → C5
```

每台 9 格；12 台共 108 格/人。

### 5.2 每台的标准动作（照着做）

A（核验预填）：

1. 在 `annotator_A.json` 里找到该固件区块；
2. 打开第 3.2 节对应的 evidence JSON，以及 `evidence_audit.md` 的同一固件区块；
3. 逐条核对 `check_code`、证据 ID、`raw_ref`；
4. 能对上就保留 `found`；对不上就改成正确值；没有证据且没实测就 `not_tested`；
5. 每台保存一次；每 3 台跑一次 JSON 校验：

```powershell
python -c "import json; json.load(open(r'materials\annotations\annotator_A.json', encoding='utf-8')); print('JSON_OK')"
```

B（独立从 TODO 填）：按第 3、4 节规则逐格填，不要看 A 文件或 `evidence_audit.md`。

### 5.3 A2 的特别说明

A2 用运行时证据 `evidence_runtime_dcs.json`：
- `CRED_DEFAULT_ADMIN_WEB`：有 E1 条目（`admin:` 空口令 → `/home.asp`），填 `found`；
- `UNAUTH_MGMT_ENDPOINT`：有 E2 条目（未认证 HNAP），填 `found`；
- `UNAUTH_INFO_DISCLOSURE`：有 E2 条目（HNAP 泄露型号/固件/MAC），填 `found`；
- 其他项没有运行时证据 → `not_tested`（除非你另外做了测试）。

A 的预填已经把 A2 的静态证据也并进来（所以比运行时 3 项多），
A 核对时要以 evidence 原文为准；B 仍独立判断。

### 5.4 全部完成后自查


如果显示不一致条目，先不要合并，进入第 8 节仲裁。

### 7.2 合并

```powershell

  materials\annotations\annotator_A.json `
  materials\annotations\annotator_B.json `
  materials\annotations\annotation_combined.json
```

### 7.3 计算指标

```powershell
python -m src.metrics materials\annotations\annotation_combined.json `
  --output materials\metrics_12.json
```

### 7.4 看结果

```powershell
Get-Content materials\metrics_12.json
```

字段解释：

| 字段 | 含义 | 怎么读 |
|---|---|---|
| `coverage` | 已标注（found+clear）格数 / 108 | 低就说明大量 `not_tested`，不要吹“全覆盖” |
| `agreement` | A/B 完全一致比例 | 受“都填 not_tested”影响，可能虚高 |
| `kappa` | 扣除随机一致后的 Cohen's kappa | 比 agreement 更可信；样本少时看不出来 |
| `decision_accuracy` | `decisions` 数组里 expected=actual 比例 | 没填 decisions 就是 `null` |
| `false_block_rate` / `miss_rate` | 策略回放误杀/漏放 | 没回放就是 `null` |
| `asn_fallback_rate` | ASN 回退策略占比 | 没 policies 就是 `null` |
| `policy_rule_count` | 策略条数合计 | 没 policies 就是 0 |

> `null` 不是 0，也不是“没有发生”；材料里写 `N/A / TODO(measure)`。

### 7.5 kappa 的粗略解释

| kappa | 粗略含义 |
|---|---|
| < 0 | 比随机还差 |
| 0–0.20 | 很弱 |
| 0.21–0.40 | 一般 |
| 0.41–0.60 | 中等 |
| 0.61–0.80 | 较好 |
| 0.81–1.00 | 很好 |

但 12×9 的样本很小，且大量 `not_tested` 会让 kappa 不稳定；报告里必须同时写 **N、agreement、coverage**，不能只报一个 kappa。

## 8. 分歧仲裁（第三人）

### 8.1 找出不一致

`check_annotations.py` 会打印：

```text
A/B 不一致: 7 个
  C2 CRED_DEFAULT_SERVICE_LOGIN: A=found B=not_tested
  ...
```

### 8.2 仲裁人怎么做

对每一条不一致：

1. 打开该固件的 evidence 文件；
2. 搜索 `check_code`；
3. 看 `level/raw_ref/detail`；
4. 判断：
   - 有对应证据 → `found`；
   - 有真实测试记录且无发现 → `clear`；
   - 都没有 → `not_tested`；
5. 在 `materials\annotations\arbitration.md` 记一行。

模板：

```markdown
| 固件 | 检查项 | A | B | 仲裁 | 依据 |
|---|---|---|---|---|---|
| C2 | CRED_DEFAULT_SERVICE_LOGIN | found | not_tested | found | evidence_sample_C2.json E-C2-0001 / etc/passwd:1 |
```

### 8.3 关键：不要覆盖 A/B

- kappa 用 **原始 A/B** 算；
- 仲裁结果只写进 `arbitration.md`，或另存 `annotator_arbitrated.json`；
- 如果把 A/B 都改成仲裁值，kappa 会变成 1.0，是假高。

### 8.4 最终交付

- `annotator_A.json`（原始）
- `annotator_B.json`（原始）
- `annotation_combined.json`
- `metrics_12.json`
- `arbitration.md`
- 可选：`annotator_arbitrated.json`

## 9. 判定正确率（可选，第二阶段）

`decisions` 数组格式：

```json
"decisions": [
  {"expected": "reject", "actual": "reject"},
  {"expected": "conditional", "actual": "conditional"}
]
```

- `expected` 只能填 `pass / conditional / reject`，来自锚点的公开已知结论；
- `actual` 从 `materials/decisions/<ID>.json` 的 `verdict` 抄；
- **只对 3 个锚点填**，不要给 12 台都编 expected；
- 不填时 `decision_accuracy` 为 `null`，这是诚实的。

## 10. 常见错误与修复

| 现象 | 原因 | 修复 |
|---|---|---|
| `未知状态: 'TODO'` | 还有 TODO | 全部替换 |
| `键集合不一致` | A/B 固件或检查项数量不同 | 用同一份 starter，不要删键 |
| `JSONDecodeError` | 少逗号/多逗号/中文引号 | 用 VS Code 红色波浪线定位；只使用英文 `"` |
| `coverage` 很低 | 大量 not_tested | 正常；不要为了指标硬填 clear |
| `kappa` 是 `null` | 只有单一类别或样本不足 | 如实写 N/A；不要造数据 |
| 终端中文乱码 | 编码问题 | `chcp 65001` + `$env:PYTHONIOENCODING="utf-8"` |
